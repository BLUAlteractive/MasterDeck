# Canonical activity ingestion

`GET /v1/activity/summary` is authenticated and owner-scoped. `POST /v1/activity/ingest` accepts only a command UUID and bounded opaque evidence reference. It never accepts a trusted step count, native JSON batch, client permission flag or chosen reward. The server verifier port must independently bind the evidence to the authenticated user before the transaction checks current account/session and activity consent again. **No production verifier is implemented or configured.** HealthKit/Health Connect reads and device attestation alone do not constitute verified server step evidence. Main returns unavailable; the existing native read screen remains diagnostic. Actual OS/device verification and the trust/abuse policy are open acceptance gates.

A reviewed server `ActivityPolicy` explicitly supplies version/approval, integer steps-per-credit, credit cap, maximum plausible rate/day, upload lookback and precision retention. The numbers in tests are TEST ONLY; the master-spec economy figures remain proposals. Each UTC day snapshots its earning policy. Records crossing UTC midnight are excluded until a trusted provider can provide real per-day totals; the server never estimates a proportional step split.

The user lock serializes all devices/sessions. Source IDs and proof references are hashed; only platform enum, coarse day, immutable accepted units/decisions and receipt/audit hashes are retained long term. Exact start/end times exist only for overlap checks during the bounded lookback. Whole intervals overlapping accepted intervals are excluded, including alternatives from another OS/device. Manual, future, stale, implausible, deleted and post-withdrawal-cutoff violations are excluded. Repeats of the same canonical source cannot mint again even with a new command/evidence reference. This conservative approach may undercount overlapping alternatives; it does not claim to reproduce each OS's authoritative aggregation.

Trail Credit allocations reference the balanced journal and are capped independently from Press steps. A single transaction may call the server-owned Press resolver and persist at most one selected Press allocation per batch, only for newly accepted canonical sources. B069 supplies real job ownership/timing/progress validation; the isolated B061 allocation fixture is not an actual Press Job or activity provider. With no selected job/resolver, activity is not saved for later job reuse. Each channel is independently idempotent; no double wallet or multiple job grant is allowed.

Changed/deleted accepted sources create immutable review records with a deterministic signed step adjustment against the original accepted source. Earning and new functional Trail Credit spending stop while review is pending. Existing journals, nonnegative balances and completed cards are not silently rewritten. **Automatic correction reconciliation and review resolution are not activated**: a reviewed operator policy must determine debt/recovery, unspent-credit adjustment, active-job reduction and already-completed-card treatment before live ingestion. Tests prove the hold and unchanged original allocations, not an invented clawback policy. Ordinary gameplay remains available subject to its existing admission rules.

A configured single-flight worker scrubs precise timestamps on retention expiry. Withdrawal and verified account deletion scrub them immediately. The latest withdrawal timestamp fences out pre-withdrawal records with fresh IDs after re-opt-in, preventing precision minimization from opening an overlap replay hole. Hashed dedupe/receipt/units and correction evidence remain under the reviewed retention policy and pseudonymous account. Owner exports add ACTIVITY and ACTIVITY_REVIEWS projections without raw health-record identifiers, device origin strings or timestamps. No raw GPS/location is involved.

Monitor fixed `activity.ingest` aggregate booleans and `activity.retention` retry status; no raw proof/user/source/health data is logged. Review queue staffing, legally approved health retention, real provider verification, native consent/revocation and B069/B080/B081 journeys remain launch gates. Rollback disables the configured verifier/worker and preserves source, review, allocation and financial evidence. Reverse SQL is exclusively for the runner-owned disposable database.
