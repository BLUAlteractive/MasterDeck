# Server billing boundary — B040

Main intentionally configures no billing or storefront policy. There is no payment-initiation button or hidden real-charge path. The server supports reviewed, single-quantity, fixed-content nonconsumable cosmetics only. Read COMMERCE_REVIEW.md before activation; fixture approvals, tokens and transactions are not real store evidence.

## Reviewed server configuration

A reviewed development bootstrap may pass `features.storefrontPolicy` and `features.billing` to `createApp`. `BillingConfig` requires an explicit environment, approval reference, 32-byte server encryption key and platform providers. Production must use the provided `appleBillingProvider` and `googleBillingProvider` factories, never the fixture provider. App startup refuses billing without configured identity/catalog. No environment variable automatically enables purchases.

For Apple, obtain public trust roots from [Apple PKI](https://www.apple.com/certificateauthority/), construct the official `AppStoreServerAPIClient` with protected App Store server signing credentials, and pass it with bundle ID, roots, environment and production appAppleId to `appleBillingProvider`. The factory always enables online certificate checks, verifies JWS and fetches fresh canonical transaction information. It uses originalTransactionId for nonconsumables so restore IDs cannot duplicate a purchase. Verified revocations take precedence. See [Apple SDK](https://github.com/apple/app-store-server-library-node), [original transaction identifiers](https://developer.apple.com/documentation/appstoreserverapi/originaltransactionid) and [restore transaction IDs](https://developer.apple.com/documentation/appstoreserverapi/transactionid).

For Google, provide the fixed package name, environment, authenticated Pub/Sub audience URL and exact notifier service-account email to `googleBillingProvider`. The official GoogleAuth client obtains server androidpublisher access through protected operator credentials/ADC. The provider always fetches ProductPurchaseV2 from Google's fixed API origin and checks complete state, exact one-item/quantity, nonconsumption, environment and account binding. Pending records grant nothing, including when completion fields are absent. Pub/Sub requires a verified Google ID token with the configured audience/email; message status is only a trigger for authoritative lookup. See [one-time lifecycle](https://developer.android.com/google/play/billing/lifecycle/one-time) and [ProductPurchaseV2](https://developers.google.com/android-publisher/api-ref/rest/v3/purchases.productsv2).

Keep signing/OAuth credentials and encryption keys in protected server secret configuration, outside the repository and all EXPO_PUBLIC variables. Added ignores cover p8/keystore/credential JSON/raw JWS files. The only checked-in certificate is public Apple Root CA G3 for rejection tests, SHA-256 `63343abfb89a6a03ebb57e9b3f5fa7be7c4f5c756f3017b3a8c488c3653e9179`; it is not a private signing key or a production enablement setting. Key rotation/retention and operational secret provisioning require review before launch.

## Protocol and durable processing

- Permanent signed-in users call `GET /v1/billing/context`. The server returns an Apple appAccountToken and Google obfuscated account binding; the native store client must use them. Guests cannot create a purchase binding. No purchase is initiated by this endpoint.
- `POST /v1/billing/verify` accepts only `{platform:'APPLE',signedTransaction}` or `{platform:'GOOGLE',purchaseToken}`. No client price, quantity, winner, owner, paid-success or grant fields. Verification and current account/session checks precede one transaction creating the immutable catalog snapshot, exactly its cosmetic grants, source event and acknowledgement job. The response only acknowledges recording; GET cosmetics determines current usability.
- `POST /v1/billing/notifications/apple` accepts signedPayload; `/notifications/google` accepts an authenticated Pub/Sub envelope. After provider authentication, normalized proof is encrypted in a durable deduplicated inbox. Workers reverify before fulfillment, retry outages and process acknowledgements after grants commit. They drain on shutdown and emit only fixed event/status logs.
- Proofs are AES-256-GCM encrypted with random nonces and row-specific associated data. No raw token or JWS appears in API views/logs. Sandbox and production identities/queues/purchases are separate; production inventory never displays sandbox grants. Duplicate receipt/notification processing converges on one canonical purchase.
- Verified refunds revoke only that purchase's cosmetic grants, preserve immutable events and cannot revive on older active receipts. No card/level/rarity/Press or wallet mutation occurs. B041 adds owner restore/reconciliation and multiple-purchase benefit handling.

## Deployment and acceptance

Before the migration, verify there are no unverified legacy CosmeticGrant rows. Adding the required purchase FK intentionally fails rather than fabricate payment evidence. Do not silently backfill a trusted receipt. Owned rollback tests erase only disposable fixtures; deployed repair must retain payment evidence and use reviewed forward migration.

Tests cover trusted fixture business flows plus real SDK rejection/strict Google response parsing and vault integrity. They do not establish successful Apple/Google sandbox purchase, native client price/binding, pending approval, refund, restore, Pub/Sub delivery, store console or production acceptance. Those require actual configured platforms/devices and the legal/product/security gates. No real credential, transaction or platform publication was used here.
