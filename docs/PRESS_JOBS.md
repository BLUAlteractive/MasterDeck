# Printing Press reservations and job state

B068 reserves a card and owned screen without granting progress or a transformed card. `POST /v1/press/jobs/start` requires fresh linked identity, reviewed Press policy, the owned card/screen IDs and their expected versions. Exactly one ACTIVE/PAUSED/READY_TO_CLAIM job may reserve an owner, card or screen. SQL partial uniqueness and the user lock back the transaction. The job snapshots immutable recipe, source card and policy; its screen becomes ASSIGNED, with append-only events and a stable command receipt.

The card remains OWNED at its old level and may be locked/unlocked by an ordinary match at the old immutable game snapshot. Start rejects a currently game-locked card. Active/paused reservations reject fusion and any direct consume/revoke/level edit, with both application and database guards. No level change, new card, screen consumption, ink debit or walking proof is implemented here.

`POST /v1/press/jobs/commands` accepts only PAUSE, RESUME or CANCEL with expected job version and stable command UUID. Repeating a committed command returns its original acknowledgement; stale versions and foreign jobs fail. Pause keeps the reservation/progress; resume records a new server active window. Cancel before any progress returns the screen as AVAILABLE and leaves the same original card unchanged. A recipe with DISABLED forbids post-progress cancellation; a separately reviewed FORFEIT_SCREEN policy revokes the screen entitlement without calling it a successful consumption or returning currency. B069 supplies actual authoritative progress/claim transitions.

A requested account deletion revokes any reserved job and its assigned screen atomically before suspension, without an upgrade or currency grant. This is permanent deletion cleanup, distinct from voluntary cancellation/refund. It leaves card/game and append-only evidence intact; existing active-game/provider cleanup gates still apply. Reservations cannot indefinitely prevent account removal.

`GET /v1/press/jobs` returns the owner's current reserved job; `GET /v1/press/jobs/:id` returns only an owner job. The API distinguishes accepted walking steps from accessible quest units and snapshots exact requirements. Neither field accepts a client counter. PRESS_JOBS privacy export returns minimized owner metadata, not a route/sample trace. Main has no reviewed Press policy; new/resumed jobs are unavailable, while owner read/pause/cancel remain available to safely shut down existing work.

Migration `202610310005_press_jobs` adds jobs/events, slot uniqueness, screen reservation links, immutable snapshots, event-chain reconciliation and card reservation guards. Reverse SQL is disposable-only and precedes the owned-screen reversal. Production rollback disables new start/resume/progress, preserves records and allows safe owner cancellation or reviewed deletion cleanup; never erase reservations or history underneath delayed commands. Existing aggregate API metrics and fixed `press.start` events omit user IDs, proofs and balances. Real device/proof/economy activation, progress and in-place claim are separate open gates.
