# Privacy operations and explicit limits

All three choices default off: optional collection analytics, activity upload and foreground location. A choice is not an OS permission, proof of steps or permission to upload a route. There is no trusted activity/location ingestion in these tickets. Existing wallet, game and fraud journals are operational records, not optional client analytics. WEC includes only current analytics opt-ins; withdrawal purges the latest collection activity timestamp. No raw coordinates, health samples, device advertising identifiers or private opponent hands are added by B051.

The authenticated `/v1/privacy` API exposes choices. POST `consent` requires a stable UUID commandId, purpose and enabled; enabling also requires the configured policyVersion. A trusted bootstrap must supply a reviewed HTTPS regional policy URL/version, approval reference, retention approval, bounded analytics retention days and a protected 32-byte HMAC key through `PrivacyConfig`. Main deliberately supplies none; opt-ins and automatic provider deletion remain unavailable. Disabling a choice is allowed without a newly approved policy. Consent history and owner export access are append-only; direct consent state changes without matching evidence fail at transaction commit.

GET `/v1/privacy/export?resource=ACCOUNT&limit=50` exports bounded owner projections. Other resources: CARDS, OWNERSHIP, PURCHASES, CONSENTS, PLAY_CHIPS, TRAIL_CREDITS, STORE_GEMS, PROGRESSION and SAFETY. Follow opaque nextCursor with the same resource. Each page is its own authenticated snapshot, not a frozen account archive. No purchase proof vault, bearer/refresh token or hidden match state is returned. Mobile displays and shares one JSON page at a time under explicit user action. These are engineering self-service projections, not a claim that a regional access request is fully answered: provider profile records, retained anti-abuse/game audit records and legal exceptions need the reviewed support process. Export before requesting deletion; a suspended/deleted token cannot retrieve records. No export is sent to another person automatically.

POST `/v1/privacy/deletion` requires `confirm: DELETE_ACCOUNT` and a command UUID. The existing owner-unique deletion request immediately suspends the user and revokes every API session, then queues an audited job. A lost acknowledgement remains unconfirmed to the client; support must look up the request through authorized operations. The managed host clears local provider credentials after an acknowledged request, with cleanup failures exposed. This does not claim provider deletion completed or erase OS HealthKit/Health Connect records.

A bounded single-flight worker processes at most 20 jobs every 30 seconds only when trusted privacy configuration exists. A scoped MFA PRIVACY_OPERATOR may audit a retry via POST `/v1/privacy/process`; no endpoint accepts a provider success flag or grants operator scope. WAITING_GAME preserves locked inventory until authoritative settlement; WAITING_CONFIG and RETRY are explicit. No invented forfeit, balance loss or client winner is used to unblock deletion. Operator capacity and backlog monitoring remain deployment responsibilities.

The Supabase adapter takes a protected service-role key and exact approved HTTPS issuer, hard-deletes the UUID identity, then independently GETs it and requires the provider's `user_not_found` response. Redirects are forbidden, requests time out, and raw responses/keys never enter application logs. Unit transports and integration proof fixtures are TEST ONLY, not evidence of an actual provider deletion. Verify the real configured project's deletion and restore behavior before activation. Provider credentials must never be EXPO_PUBLIC or committed.

Only after all identities have provider confirmations does one local transaction replace external subjects with issuer-scoped HMAC tombstones, remove sessions, collection preferences/selections and optional telemetry, revoke operator scopes, and mark COMPLETED_WITH_RETAINED_RECORDS. SQL completion guards require evidence, masked identities and no locked cards/sessions. Persisted cards, append-only ownership/consent/security/game records, purchase/refund evidence and balanced wallet journals remain under the retained pseudonymous user ID. This is **pseudonymization with retained records**, not complete anonymization or a legal retention approval. Existing purchase reconciliation may still revoke/confirm earlier entitlements; it cannot create a new purchase for an inactive account.

Keep the HMAC key separately protected and backed up with restricted recovery access. It prevents an old valid identity token from recreating a deleted account, without keeping its raw subject. Missing key configuration fails closed for an issuer with tombstones. Do not rotate/discard this key without a reviewed migration of protection; key recovery, retention periods, provider backup erasure and request completion notices require owner/privacy approval. The 30-day setting in tests is a fixture, not the live policy.

Rollback: deactivate the configured worker/provider and restore compatible application code while preserving requests, proofs, consent and tombstones. The reverse SQL is strictly for the owned disposable test database, never a production erasure/rollback procedure. Audit fixed-name `privacy.deletion`/`privacy.worker` retry logs and job statuses; no subject, token or raw provider response is logged. Production release remains gated on legal policy/retention, real provider deletion, device cleanup, operational SLOs and future activity/route TTL tests.
