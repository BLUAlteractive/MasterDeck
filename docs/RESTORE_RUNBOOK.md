# Backup and clean restore runbook

Run `pnpm ci:recovery` with Docker available. It owns a new loopback-only PostgreSQL 17 container with a random database/password and no persistent volume, ignores caller DATABASE_URL, builds current packages, deploys twice, seeds and runs database acceptance. It then creates a custom-format `pg_dump` from the frozen fixture database and restores it with `pg_restore --exit-on-error --single-transaction --no-owner --no-privileges` into a second empty database. It never resets a developer database. The dump stays in process memory, bounded to 128 MiB; this is an engineering drill, not a large-production backup service.

The verifier requires the owned random database naming scheme and a second database on the same loopback host, port and credentials. It compares sorted SHA-256 fingerprints and row counts for **every public table**, including migrations, private event chains, card instances/ownership, wallet journals, purchases and deletion tombstones. It then independently reconstructs every poker and Spades room from genesis through all commands using the authoritative replay validators on both copies. Settled poker allocations and Spades winner/team records must match recomputed state. There must be nonzero settled evidence for both games. Reconciled wallet balances, zero total Play Chips and nonmissing ownership origins are checked again. No raw row, deck, token, evidence vault or connection string is printed.

Original repository foundation art and mobile assets are archived from prevalidated regular files, extracted into a private temporary directory and compared by relative path and SHA-256. Symlinks/nonregular assets are rejected; no caller-supplied tar is extracted. Temporary archive permissions are private via its 0700 parent. Restored database and temporary assets are cleaned in finally blocks; the outer runner removes the entire owned container even on failure. After successful recovery, the runner still exercises every disposable reverse migration, reset/reseed and the complete database suite a second time. Reverse SQL is not a production recovery method.

The aggregate `recovery.drill` line reports dump digest/size, database restore time, fully verified recovery time, asset count/digest, table/row counts, replay counts/digest and invariant results. Timing starts immediately before dump creation and ends after data/replay/assets checks; it excludes initial fixture build/test and later rollback/reset. Copy only this aggregate line into an evidence report. Actual snapshot contents and credentials must never be committed. `.dump`, `.backup`, compressed SQL and private backup directories are ignored and the tracked-secret gate additionally rejects private backup artifacts.

## Production activation requirements

No production database, object store, KMS, backup scheduler or recovery operator was configured by B052. Do not treat the measured local fixture recovery time as a production RTO, or its frozen snapshot as a production RPO. Owners must approve actual workload-dependent RPO/RTO targets, backup frequency/retention, encrypted offsite storage, immutable generations, access separation, alerts and scheduled clean restore evidence. Confirm PostgreSQL service-supported PITR/WAL coverage and host-loss recovery before claiming either. Do not invent numeric operational promises from this laptop measurement.

Back up database snapshots/WAL and legally licensed immutable asset manifests/blobs at matching versions. Separately protect recovery access to managed identity configuration, receipt-verification credentials, purchase-vault keys, privacy HMAC/tombstone key and operator MFA recovery. Provider signing/JWKS and platform APIs have their own availability policies. This fixture proves encrypted purchase evidence survives byte-for-byte; it does not prove production key custody or decryptability after host loss. Hashes are integrity comparisons, not legal provenance, encrypted backup authentication or signatures.

For an actual authorized recovery: isolate a new environment with outbound billing/reward/deletion workers disabled; restore compatible schema/data/assets and separately recover protected key versions; run integrity/replay checks without exposing private payloads; compare authoritative provider purchase/refund state before opening commerce; verify deletion tombstones and do not reintroduce previously erased provider identities or expired route traces. Reapply deletion/retention requests newer than the chosen snapshot under reviewed policy before admitting users. Keep production writes paused until a named operator and independent reviewer record evidence, outcomes and remaining gaps. Switch traffic only after explicit approval; retain the source environment for investigation without exposing its data.

If restore/replay differs, fail closed, preserve restricted evidence and investigate the exact snapshot/build/key versions. Never repair balanced history by editing journals, minting replacement cards, overwriting outcomes or deleting immutable events. Use audited forward corrections and source-idempotent reconciliation. If a rollback is needed, disable affected features and roll application traffic to a compatible validated artifact while retaining durable evidence; do not run disposable down-migration scripts in production.
